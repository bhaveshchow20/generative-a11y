<span id="agent&#45;lifecycle"></span>

## Agent interfaces have more states than a chat transcript

An agent can start a long&#45;running tool, report progress, request a decision,
lose its connection, retry, and finish with a result. Visual indicators may make
these transitions obvious, while a screen&#45;reader user remains on the
composer, transcript, or another part of the page.

Accessibility depends on communicating consequential state changes without
narrating every internal operation. Announcements should describe the
user&#45;facing lifecycle, not expose raw tool payloads, backend errors, or
chain&#45;of&#45;thought&#45;like implementation detail.

<span id="event&#45;model"></span>

## Map confirmed agent state to normalized events

Choose events from confirmed application state. Tool argument streaming does not
establish that execution started; a disappearing approval control does not
establish that a decision was submitted. Keep stable IDs across each operation
and attach an instance ID when work can retry.

| Agent state          | Normalized event           | Announcement purpose                              |
| -------------------- | -------------------------- | ------------------------------------------------- |
| Tool begins          | tool.started               | Set context for a user-relevant operation         |
| Meaningful milestone | tool.progress              | Report progress without flooding                  |
| Approval needed      | interaction.requested      | Make a required decision discoverable             |
| Tool fails           | tool.failed                | Communicate the safe user-facing failure label    |
| Response retries     | response.retrying          | Cancel stale response work and identify the retry |
| Connection changes   | connection.lost / restored | Report confirmed availability changes             |

<span id="priority&#45;and&#45;focus"></span>

## Prioritize decisions and failures without stealing focus

An AI agent approval request should be announced as a confirmed request for
input, while the approval control remains part of the host application’s normal
keyboard and focus model. Routine progress can stay polite; required decisions
and safe failure labels can receive higher priority. The event stream must keep
each update attached to a stable response, tool, or approval identity so stale
work can be cancelled after retries and interruptions.

If an approval control needs focus, the host application makes that interaction
decision through its accessible dialog, disclosure, or inline workflow. See
[interactions and approvals](/docs/lifecycle/interactions) for the event
contract.

Bounded queues and terminal&#45;event cleanup prevent outdated progress from
being delivered after a retry, failure, interruption, or disposal.

<span id="framework&#45;fidelity"></span>

## Choose an adapter by observable lifecycle fidelity

The AI SDK, assistant&#45;ui, and AG&#45;UI adapters translate documented public
framework state into the normalized event model. Their pages list what they can
observe. When the host application knows about additional connection, retry, or
approval states, it can dispatch those core events directly instead of asking an
adapter to infer them from rendered UI.
