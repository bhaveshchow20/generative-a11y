## Install for your existing app

```shell
npm install @generative-a11y/react @generative-a11y/ai-sdk
```

Your existing AI SDK setup must also satisfy its `zod` peer
(`^3.25.76 || ^4.1.8` for the checked SDK version).

These are the only two direct library dependencies for this recipe. The React
package installs core and DOM as dependencies. If you later import either
package yourself, declare it directly too.

Your app must already have Node.js 22+, `ai@7.0.x`, `@ai-sdk/react@4.0.x`, and
compatible `react` and `react-dom` peers (`^18.2.0 || ^19.0.0`). The checked
versions are ai 7.0.77, @ai-sdk/react 4.0.80, and React / React DOM 19.2.8.
Keep your existing backend and transport; this library does not create them.

## React integration

Add these imports and keep your existing options in `defaultOptions`. The
example transport uses `/api/chat`; retain your endpoint, authentication, and
other transport configuration. Keep this module behind a `"use client"`
boundary in a React Server Components app.

```tsx
"use client";

import { useState } from "react";
import type { UIMessage } from "ai";
import { DefaultChatTransport } from "ai";
import { useChat, type UseChatOptions } from "@ai-sdk/react";
import { A11yProvider, useRuntime } from "@generative-a11y/react";
import {
  useChatAccessibility,
  useObserveChatAccessibility,
} from "@generative-a11y/ai-sdk/react";

// Keep your existing transport and options here (or pass them to App).
const defaultOptions = {
  id: "support",
  transport: new DefaultChatTransport({ api: "/api/chat" }),
};

// This recipe lets useChat construct the chat; an existing Chat needs callbacks
// composed at its own construction boundary instead.
type ChatOptions = Exclude<UseChatOptions<UIMessage>, { chat: unknown }>;
```

Wrap your existing `Chat` once and accept its options as props:

```tsx
export function App({ options = defaultOptions }: { options?: ChatOptions }) {
  return (
    <A11yProvider>
      <Chat options={options} />
    </A11yProvider>
  );
}
```

Inside `function Chat({ options }: { options: ChatOptions })`, replace the
existing `useChat` call with this wiring. It preserves all options and composes
your finish/error callbacks. Keep using `chat` in your existing UI.

```tsx
const runtime = useRuntime();
  const accessibility = useChatAccessibility({
    runtime,
    scopeId: "support",
    onFinish: (event) => options.onFinish?.(event),
    onError: (error) => options.onError?.(error),
  });
  // Spread composed callbacks last so host options cannot overwrite them.
  const chat = useChat({ ...options, ...accessibility.chatCallbacks });
  useObserveChatAccessibility({ integration: accessibility, snapshot: chat });
```

See the [complete copyable component](/api/ai-sdk/use-chat-accessibility) for a
minimal message list and composer. The provider owns runtime and live-region
delivery, with cleanup on unmount. Keep it mounted across responses. The adapter
owns only its observer; keep `scopeId` stable for that mounted session and
remount deliberately when switching chats.

This recipe lets `useChat` construct the chat. With `useChat({ chat: existingChat })`,
other initialization options, including callbacks, are ignored. Compose callbacks
when constructing that chat using the [observer API](/api/ai-sdk), and manage
its subscription and cleanup at that boundary.

The result is paced live-region updates for supported response and tool events.
Your visible interface stays intact, and ordinary streaming never moves focus.
Your app still supplies semantic structure, usable keyboard controls, accessible
message content, and approval UI. DOM checks do not prove screen-reader output.

## Lifecycle mapping

The observer maps documented message parts and chat status to response, text,
tool, approval, and citation events. Composed callbacks confirm completion and
failure. Automatic retry and regenerate events are unavailable. Public AI SDK state
does not identify every retry request; do not construct adapter-owned response
IDs or fabricate retry events. The next supported public response lifecycle
is still observed normally.

- messages and status identify active response text and known tool states
- onFinish confirms completion or stop details
- onError confirms failure without copying raw error text

<span id="screen&#45;reader&#45;behavior"></span>

## Expected screen&#45;reader behavior

Core groups streaming text into paced announcement intents and gives approval,
failure, and completion updates suitable priority. The DOM package writes those
intents to live regions without moving focus during routine status changes.
Browser transcripts confirm DOM delivery; test VoiceOver, NVDA, or another
target screen reader before making support claims.

<span id="fidelity"></span>

## What the adapter can report

Use supplied callbacks so the adapter knows when a response finishes, stops, or
fails. Status alone does not provide enough detail. Retry/regenerate detection is unavailable; the adapter does not expose a retry wrapper. A successful finish after a disconnection reports recovery.

- Exports adapterInfo, createChatObserver, composeChatCallbacks
- React subpath exports useChatAccessibility and useObserveChatAccessibility
- Tool failure, approvals, and citations use stable public part IDs

<span id="troubleshooting"></span>

## Troubleshooting

Missing completion updates often mean useChat captured callbacks before the
accessibility integration created them. Repeated output can indicate an unstable
scopeId or more than one observer attached to the same chat. Inspect runtime
diagnostics, then compare the observed public state with the lifecycle mapping
above.

- Create the integration before constructing useChat.
- Keep scopeId stable for the lifetime of one chat instance.
- Use the lifecycle lab to inspect deterministic browser updates before testing
  assistive technology.

The example uses your existing AI SDK `/api/chat` endpoint. `A11yProvider`
owns the runtime and browser delivery; `useChatAccessibility` owns only its
observer. Both clean up on unmount. Keep your existing transport and UI.
Add host `onFinish`/`onError` callbacks to `useChatAccessibility` when needed;
it composes them with its own callbacks. Do not overwrite `chatCallbacks`
after spreading them into `useChat`.
